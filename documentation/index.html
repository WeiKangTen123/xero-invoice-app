Background processing
Email processing flow
The IMAP watcher detects new emails instantly via IDLE keepalive with a 60 s poll as fallback. Emails from the last 40 days are scanned on first start.
📬

Email detected

IMAP IDLE fires within seconds of a new email arriving. A 3 s debounce prevents double-scans when a user marks an email as unread. Fallback: active polling every 60 s.

⚙️

Parser branches

PDF attachments → LLM parsing (up to 5 concurrently, rate-limited). Emails with "Client / Customer:" in the body → regex template parsing, no LLM call needed.

🤖

LLM extraction

Gemini is tried first. On failure, Nvidia then OpenRouter. On 429 rate-limit: waits attempt × 15 s (up to 4 retries). If all LLM calls fail, falls back to a regex parser.

🖼️

Scanned PDFs

Image-only / scanned PDFs with no extractable text cannot be parsed by the LLM. They are saved and marked review-needed so the user can enter data manually.

🔄

Boot recovery

On server start, all pending and submitting invoices are retried sequentially (1.5 s gap) 3 s after startup. No invoices left stranded after a crash or redeploy.

🗑️

Clear all

Stops the watcher, clears the email queue, deletes all PDF files, and resets the invoice store — a clean slate for the user without affecting other users.

pending

Awaiting submission

Parsed and stored locally. Queued for Xero or waiting for Auto-submit to be enabled. Boot retry picks these up after restart.

reviewed

Verified, not yet posted

User manually verified the extracted data. Shown in blue — visually distinct from posted (green). A banner in the invoice list prompts the user to click "Post to Xero".

submitting

Claimed & in-flight

claimForSubmit() atomically sets this inside a write lock. No concurrent caller can claim the same invoice — duplicate submissions are impossible.

posted

Live in Xero

Draft invoice created. xeroInvoiceId stored. PDF and email body attached to the Xero record. Locked — cannot be changed.

error

Xero rejected

Real Xero validation message stored in errorMsg. Fix the field in InvoiceReview and click Post again — submission is idempotent.

review-needed

LLM parse failed

Amount or invoice number could not be extracted (e.g. scanned/image PDF). Record stored for manual data entry. Never submitted to Xero automatically.

reported

Flagged by user

User added a note describing a problem. Visible to admins in the Admin panel under "Flagged invoices". Can be resolved by an admin.

duplicate

Blocked as duplicate

Matched an existing record by vendor + invoice# + amount (±1%). Stored for visibility but never sent to Xero. Locked — cannot be changed.

Currency handling
PDF currency first, org base currency as fallback
The system never hardcodes a fallback currency. It detects the Xero org's actual base currency on the first mismatch and caches it — works for any Xero org worldwide.
1

Extract currency from PDF

LLM reads the PDF and extracts the currency code (SGD, JPY, EUR…). Used directly on first submission.

invoiceData.currency → "SGD"
2

Submit to Xero in PDF currency

Calls createInvoices() with the extracted currency. If the org supports it, done.

currencyCode: "SGD" → POST /Invoices
3

Rejected: currency not subscribed

Calls GET /Organisations to read the org's actual base currency (e.g. NZD for Xero Demo).

GET /Organisations → baseCurrency: "NZD"
4

Retry with org base currency

Invoice resubmitted in base currency. Stored currency field updated. Base currency cached per tenant for server lifetime.

currencyCode: "NZD" → invoice created ✓
🌍

Works for any Xero org

NZD (Demo), AUD, GBP, SGD — whatever the org's base currency is, the system detects it automatically. No hardcoded fallback.

⚡

Cached per tenant

Base currency fetched once on first mismatch, stored in memory for the server lifetime. No extra API call for subsequent invoices.

🔧

Enable currencies in Xero

Xero → Settings → Currencies → Add currency (e.g. SGD). Once added, future invoices post in the extracted PDF currency — no fallback needed.

Deduplication
Two layers of duplicate protection
Duplicates are blocked at two distinct points using different matching strategies. Vendor names are normalised so legal suffix variations never slip through.

Layer 1 — Storage dedup

Before storing, findStored() checks for a matching record. Matches vendor (normalised) + invoice# + amount within 1%.

// in onInvoiceEmail — before any storage const existing = invStore.findStored( invoiceData.vendorName, invoiceData.invoiceNumber, invoiceData.invoiceDate, invoiceData.totalAmount ); if (existing) { return; // never stored, never sent to Xero }

"BLCKLB PTE. LTD." and "blcklb" → same vendor. "Miss Thitipat Srikhongnattakul" and "Thitipat Srikhongnattakul" → same vendor.

Layer 2 — Atomic Xero claim

claimForSubmit() checks status and writes inside a single file-mutex lock. Two concurrent callers can never both claim the same invoice.

// atomic check + flip inside write lock function claimForSubmit(id) { return _withLock(() => { if (inv.status === 'posted') return { claimed: false, reason: 'already posted' }; if (inv.status === 'submitting') return { claimed: false, reason: 'already submitting' }; inv.status = 'submitting'; // ← atomic flip _write(list); return { claimed: true }; }); }

Real number (e.g. 040526-3)Same normalised vendor + same invoice# (case-insensitive) + amount within 1%

Data isolation
Fully per-user data separation
Every resource that touches invoice data is scoped to a single user. Multiple users share the same server with zero data leakage between them.
Per-user data path: main/data/users/{userId}/ — config.json (IMAP + Xero + LLM creds) · settings.json (autoProcess toggle) · invoices.json (max 500) · pdfs/ (PDF files)
Directory is created immediately on account registration. On every boot, ensureUserDirectories() re-creates any missing directories (safe no-op if already present).

PDF Viewer — Signed URL authentication
Browsers cannot send custom Authorization headers on direct navigation (new tab, <iframe src>, <embed>). A two-step signed URL flow solves this.
1

Request signed URL

Frontend calls GET /api/invoices/:id/pdf-url with Bearer JWT. Server verifies JWT, checks the PDF file exists on disk, issues a short-lived token scoped to that userId + invoiceId, valid for 5 minutes.

2

Open PDF directly

<iframe src="/api/invoices/:id/pdf?token=xxx"> — no Authorization header needed. Server verifies the token scope, streams the PDF. Frontend refreshes the token every 4 minutes while the review page is open.

⏱️

Rate limiter (per user)

Sliding 60 s window — max 15 requests per minute, max 5 concurrent. Provider: Gemini (15 RPM free tier) → Nvidia → OpenRouter.

🔄

429 back-off

On rate-limit: waits attempt × 15 s before retry. Up to 4 attempts before falling back to the regex parser. No invoices are dropped.

📜

Regex fallback

If all LLM attempts fail, a pattern-based regex parser attempts to extract key fields. Invoice saved as review-needed if extraction is still insufficient.

Deployment
Railway & local development
The app runs as a single Node.js process. No database required — all data is stored as JSON files on disk. Railway provides free persistent storage.
Deploy to Railway
1

Push to private GitHub repo

Never commit .env. The .gitignore excludes it by default.

2

New Railway project

Railway → New Project → Deploy from GitHub repo. Select your repo.

3

Set environment variables

Add JWT_SECRET (required) and optionally SLACK_WEBHOOK_URL, REDIS_URL.

4

Generate domain

Settings → Domains → Generate Domain. Railway runs the app with node main/index.js (from Procfile).

5

First-time setup

Visit the URL → Register (first user = admin) → Setup page → fill in IMAP, Xero, LLM → Dashboard → Start.

Run locally
# Install backend deps npm install # Start both backend + frontend (concurrently) npm run dev # Frontend only (proxies API to :3000) cd ui && npm install && npm run dev # Production UI build (served by Express) cd ui && npm run build # Backend only (nodemon auto-restart) npm run dev:server
npm run dev runs three scripts in order:
1. predev — kills anything on port 3000 before starting
2. dev:server — nodemon with 500 ms delay (grace period for port release)
3. dev:ui — Vite dev server for React frontend

On SIGTERM / SIGINT, the server calls server.close() before process.exit() — releases the port immediately so nodemon can restart without EADDRINUSE.
Key capabilities
What the system handles for you
Production-grade reliability — no in-memory state that a restart can lose, no hardcoded limits that break at scale.
🔁

Boot-time retry

3 s after startup, all pending / submitting invoices across all users are retried sequentially. No invoices left stranded after a crash.

📊

Persistent pipeline panel

Pipeline Status widget in the sidebar via shared React context — always visible regardless of which page you navigate to. Polls 3 s (active) / 15 s (idle).

💱

Dynamic currency fallback

PDF currency tried first. On rejection, org base currency fetched from GET /Organisations and cached. Works for any Xero org worldwide.

🔒

Atomic dedup lock

claimForSubmit flips status to submitting inside a single write-locked operation. Concurrent callers are guaranteed to never double-post.

🏎️

Rate-limit aware

Xero calls spaced 1.5 s apart. withRetry reads the Retry-After header on 429s and waits the exact amount before retrying — up to 5 attempts.

🔍

Real Xero error messages

_parseXeroErr decodes xero-node's nested JSON-string errors so you see the actual Xero message ("Invoice # must be unique"), not "Unknown Xero error".

🧹

Smart dedup matching

Vendor names normalised (strips Pte. Ltd., K.K., LLC, Inc…). Same invoice# with different amounts treated as distinct — allows legitimate corrections.

📎

PDF + email attachment

Original PDF and email body text attached directly to the Xero draft invoice — full context for your accountant without leaving Xero.

🔐

Write safety

Each user's invoice store has its own _writeLock promise chain. Concurrent email processing for the same user never corrupts invoices.json. Different users never block each other.
